## INTEGRATION 1 — IPRS Patient Identity Verification

### What It Does
Verifies patient identity against the National Population Register
using their National ID or Passport number. Returns full name,
date of birth, gender, and address. Replaces manual data entry
and prevents duplicate or fraudulent registrations.

### What We Have Built
- verify_patient_identity() PL/pgSQL stub RPC in Supabase
- "Verify identity & SHA status" button on registration form
- Consent OTP dialog before calling the API
- patients.identity_verified column
- patients.identity_verified_at column
- patients.identity_verified_by FK to auth.users

### Credentials Needed
- DHA developer account: https://developers.dha.go.ke
- IPRS API client ID and secret
- Facility KMHFL code (already in app_settings)
- DHA Provisional Interoperability Accreditation certificate

### Sandbox Environment
- URL: https://sandbox.dha.go.ke/iprs/v1/verify
- Test NID numbers provided by DHA upon sandbox access

### Activation Steps

**Step 1 — Get credentials**
1. Visit https://developers.dha.go.ke
2. Register facility using KMHFL code
3. Request IPRS API access
4. Receive: client_id, client_secret, sandbox URL

**Step 2 — Add secrets in Supabase Dashboard**
Go to Edge Functions → Secrets and add:
- IPRS_CLIENT_ID
- IPRS_CLIENT_SECRET
- IPRS_API_URL = https://sandbox.dha.go.ke/iprs/v1/verify
- FACILITY_KMHFL_CODE = your KMHFL code

**Step 3 — Create Edge Function**
Create: supabase/functions/verify-identity/index.ts

The function must:
1. Validate caller JWT
2. Get OAuth token from DHA
3. POST to IPRS API with payload:
   { identifier, consent: "1", consent_collected_by: KMHFL_CODE }
4. If patient_id provided, update patients table with verified data
5. Return: { connected: true, found: true, iprs_data: {...} }

**Step 4 — Update frontend**
In src/routes/register-patient.tsx, update doVerification():
Replace supabase.rpc("verify_patient_identity") with:
supabase.functions.invoke("verify-identity", { body: {...} })

**Step 5 — Deploy and test**
supabase functions deploy verify-identity

## INTEGRATION 2 — SHA Member Registry

### What It Does
Verifies a patient's SHA membership status in real time.
Returns: member number, relationship to principal,
active/inactive status, fund type (PHF/SHIF), dependants.

### What We Have Built
- patients.sha_membership_status column
- patients.sha_membership_verified_at column
- patients.sha_member_number column
- SHA status badge on patient profile, accounting, insurance desk
- Warning in InsuranceDialog if status is inactive

### Credentials Needed
- SHA provider portal: https://provider.sha.go.ke
- SHA facility provider number (in app_settings)
- SHA API OAuth2 credentials

### Sandbox Environment
- URL: https://api.sandbox.sha.go.ke/v1/members/verify

### Activation Steps

**Step 1 — Register on SHA provider portal**
1. Visit https://provider.sha.go.ke
2. Request API credentials
3. Receive: SHA_CLIENT_ID, SHA_CLIENT_SECRET

**Step 2 — Add secrets**
- SHA_CLIENT_ID
- SHA_CLIENT_SECRET
- SHA_API_URL = https://api.sandbox.sha.go.ke/v1
- SHA_PROVIDER_NO = your provider number

**Step 3 — Add SHA call inside verify-identity Edge Function**
After the IPRS call, add a parallel SHA API call:
POST to SHA_API_URL/members/verify
Body: { id_number, id_type }
Returns: member_number, status, relationship, fund_type

Update patients table with SHA fields after successful response.

## INTEGRATION 3 — SHA Notification Number

### What It Does
Every SHA encounter requires a unique notification number
generated by the SHA backend at visit initiation. This number
is the primary reference for all downstream claims.

### What We Have Built
- encounters.sha_notification_number column
- Temporary placeholder: TEMP-SHA-{timestamp}-{encounter_id}
- InsuranceDialog captures and saves the number
- FHIR encounter includes sha_notification_number as identifier

### Activation Steps

**Step 1 — Create sha-notify Edge Function**
At encounter creation, call SHA eligibility API to get
the real notification number.

**Step 2 — Update encounter creation flow**
After creating encounter (registration or check-in),
call sha-notify and save the returned notification_number
to encounters.sha_notification_number immediately.

**Step 3 — Background migration**
After going live, run a script to swap all TEMP- prefixed
notification numbers with real SHA transaction IDs for
any encounters created during the stub period.

```sql
-- Identify encounters needing real notification numbers
SELECT id, sha_notification_number
FROM encounters
WHERE sha_notification_number LIKE 'TEMP-SHA-%'
AND payment_mode = 'insurance'
ORDER BY created_at DESC;

INTEGRATION 5 — AfyaLink HIE (FHIR Sync)
What It Does
Syncs clinical records to the national Health Information Exchange. Only fires when patient has consented (hie_data_sharing_consented=true). Required for DHA certification.

What We Have Built
generate_fhir_encounter(UUID) PL/pgSQL RPC (FHIR R4 compliant)
fhir-patient Edge Function (deployed)
fhir-encounter Edge Function (deployed)
fhir-condition Edge Function (deployed)
FhirSyncHandler in claims-dispatcher (stub with consent check)
patient_consents.hie_data_sharing_consented boolean
FHIR preview in InsuranceDialog and Admin Queue Monitor
What DHA Will Validate
FHIR R4 Patient resource (fhir-patient)
FHIR R4 Encounter resource (fhir-encounter) including:
ICD-11 diagnoses from encounter_diagnoses
SHA notification number as identifier
SHA fund type as serviceType
Practitioner reference (created_by user)
Facility KMHFL code as serviceProvider
FHIR R4 Condition resource (fhir-condition)
Credentials Needed
DHA AfyaLink: https://afyalink.dha.go.ke
OAuth2 client credentials
FHIR server base URL
DHA certification (Form HMIS 4)
Activation Steps
Step 1 — Apply for DHA certification

Submit Form HMIS 4 at https://certification.dha.go.ke/process
Generate sample FHIR output to attach: SELECT generate_fhir_encounter('any-encounter-uuid-here');
Validate at https://validator.fhir.org
DHA review takes 4-8 weeks
Step 2 — Receive Provisional Interoperability Accreditation Valid 6-12 months. Grants AfyaLink sandbox access.

Step 3 — Add secrets

AFYALINK_CLIENT_ID
AFYALINK_CLIENT_SECRET
AFYALINK_FHIR_BASE_URL = https://sandbox.afyalink.dha.go.ke/fhir
AFYALINK_TOKEN_URL = https://sandbox.afyalink.dha.go.ke/oauth/token
Step 4 — Update FhirSyncHandler in claims-dispatcher

Verify patient consent (already coded)
Get OAuth token from AfyaLink
Build FHIR Bundle (Patient + Encounter + Condition)
POST Bundle to AfyaLink FHIR endpoint
Record HIE response ID in dha_outbound_queue.response
Update queue status to 'sent' or 'failed'
Step 5 — Deploy and test supabase functions deploy claims-dispatcher

Test: Register patient with HIE consent → complete encounter → trigger sync → verify in AfyaLink sandbox portal.

What We Have Built
consent-dialog.tsx with full OTP flow (Track A working)
consent_otps table (SHA-256 hashed, 10-min expiry)
On-screen OTP working end-to-end in production
Legal disclaimer text hardcoded per SHA Act 2023 S.48
Legal SMS Text (MANDATORY — SHA Act 2023 S.48)
AEGISCARE: Your verification code for care visit is {OTP}. Valid for 10 mins. By sharing this code, you consent to treatment and SHA claims processing under Sec 48 of the Social Health Insurance Act 2023. False statements carry statutory penalties.

Credentials Needed

API key
Sender ID "AEGISCARE" registered and CA Kenya whitelisted (Communications Authority whitelist takes 2-4 weeks)

Visit https://africastalking.com
Create application → get API key
Go to SMS → Sender IDs → Register "AEGISCARE"
Submit CA approval with facility registration certificate
Wait 2-4 weeks for CA whitelist approval
Step 2 — Add secrets

AT_API_KEY
AT_USERNAME
AT_SENDER_ID = AEGISCARE
AT_ENVIRONMENT = sandbox (change to production when ready)
